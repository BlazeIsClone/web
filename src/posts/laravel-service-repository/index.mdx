One of Sri Lanka’s largest paint manufacturers required a high-precision distribution network. Their primary challenge was a heavy reliance on manual dispatching, where routing expertise was localized within a single manager.
This person dependency created a fragile workflow that hindered delivery agents and limited scalability. To modernize, we collaborated and transitioned to a unified, automated system capable of 100+ daily bulk deliveries. This shift to a data-driven model eliminated fragmented workflows, increased delivery accuracy, and established the scalable infrastructure necessary to maintain their market leadership.

- Backoffice: Fully integrated process of managing distributors, customers, fleet and delivery agents.
- Auto Route Optimization: Google Maps Fleet API for delivery sequencing, reducing fuel and trip durations.
- Third-Party Integration: Developed a Multi-Vendor Order API for external organizations to sync orders instantly.
- GPS Tracking: Live vehicle tracking via Wialon API and reporting to provide analytics of the operation.
- Agent App: Mobile app provides agents with delivery routes, QR codes for pickup and proof-of-delivery.

## Building The Modular Monolith

We wanted separation of concerns and started with a simple layered approach. Service repository pattern! Three layers, presentation over business logic over data access, and the middle one is [Fowler's Service Layer](https://martinfowler.com/eaaCatalog/serviceLayer.html). Note it counts to three. The model is not a layer, it is what travels through them, which is a claim I walk back a few sections down.

## What a dispatch has to be sure of

Before a run leaves the depot, five things have to be true at the same moment. The run is still a draft. Every order on it is released and belongs to that depot. The load fits the truck. The truck is not in the workshop and not already out on another run that day. The driver holds the licence class for it.

That was the manager's job. Five checks, in his head, 100+ times a day.

Our first version put all five in the controller, because that is where the request already was.

```php
class DispatchController extends Controller
{
    public function store(Request $request, int $runId): RedirectResponse
    {
        $run = DeliveryRun::with('orders.items')->findOrFail($runId);
        $vehicle = Vehicle::findOrFail($request->integer('vehicle_id'));

        if ($run->status !== 'draft') {
            return back()->withErrors('Run has already gone out.');
        }

        $load = 0;

        foreach ($run->orders as $order) {
            if ($order->status !== 'released' || $order->depot_id !== $run->depot_id) {
                return back()->withErrors("Order {$order->number} is not ready.");
            }

            $load += $order->items->sum(fn ($item) => $item->quantity * $item->unit_weight_kg);
        }

        if ($load > $vehicle->payload_kg) {
            return back()->withErrors("Load is {$load}kg, {$vehicle->registration} takes {$vehicle->payload_kg}kg.");
        }

        // maintenance window, run clash, licence class, then the writes
    }
}
```

Nothing wrong with that. For one screen it is the least code that could possibly work, and the half I cut for length is more of the same.

It stops being cheap when a second caller shows up. The Multi-Vendor Order API auto-dispatches synced orders, and the agent app reassigns a run when a truck breaks down mid-route. Same five checks, three entry points. Paint is heavy, so the payload check is the one keeping an axle legal, and three copies of a rule is three chances for one of them to fall behind.

## Four files, one dispatch

Same rules, moved. The controller keeps only the parts that are about HTTP:

```php
class DispatchController extends BackofficeBaseController
{
    public function store(DispatchRunRequest $request, int $runId): RedirectResponse
    {
        $result = $this->dispatchService->dispatchRun(
            runId: $runId,
            vehicleId: $request->integer('vehicle_id'),
            driverId: $request->integer('driver_id'),
        );

        if ($result->rejected()) {
            return back()->withErrors($result->reason);
        }

        return redirect()
            ->route($this->runRoutePath::SHOW, $runId)
            ->with('success', $this->dispatchMessage->onItsWay($result->stopCount));
    }
}
```

The service hands back a small result object: whether the run went out, and if not, why. That is everything the controller needs, and it is why the same service can answer a backoffice screen, an API call, or a phone in a truck without ever knowing which one it is talking to.

The service is where the five checks live now, ordered cheapest to fail first:

```php
class DispatchService extends BaseService
{
    public function dispatchRun(int $runId, int $vehicleId, int $driverId): DispatchResult
    {
        $run = $this->runRepository->getDraftWithLoad($runId);

        if (! $run) {
            return DispatchResult::reject($this->dispatchMessage->notDraft());
        }

        $held = $run->orders->reject(fn (Order $order) => $order->isReleasedFrom($run->depot_id));

        if ($held->isNotEmpty()) {
            return DispatchResult::reject($this->dispatchMessage->ordersHeld($held->pluck('number')));
        }

        $vehicle = $this->vehicleRepository->getAvailableOn($vehicleId, $run->scheduled_for);
        $driver = $this->driverRepository->getRosteredOn($driverId, $run->scheduled_for);

        if (! $vehicle || ! $driver) {
            return DispatchResult::reject($this->dispatchMessage->crewUnavailable());
        }

        if ($run->payload_kg > $vehicle->payload_kg) {
            return DispatchResult::reject($this->dispatchMessage->overloaded($run->payload_kg, $vehicle));
        }

        if (! $driver->licensedFor($vehicle->class)) {
            return DispatchResult::reject($this->dispatchMessage->wrongLicence($vehicle->class));
        }

        $stops = $this->routeOptimizer->sequence($run->depot, $run->orders);

        return DB::transaction(function () use ($run, $vehicle, $driver, $stops) {
            $this->runRepository->replaceStops($run, $stops);
            $this->runRepository->markDispatched($run, $vehicle, $driver);

            RunDispatched::dispatch($run);

            return DispatchResult::dispatched($stops->count());
        });
    }
}
```

Read it for what is missing. There is no SQL anywhere in there, and no hint of how expensive any of those lookups are. The method is the rulebook, top to bottom, and the rulebook is the part the business actually argues about. When ops asks why a run was refused, this is the file you open, and you can answer the question without reading a single query.

The repository owns the queries and the writes that come in pairs:

```php
class DeliveryRunRepository extends BaseRepository
{
    public function getDraftWithLoad(int $runId): ?DeliveryRun
    {
        return $this->run
            ->draft()
            ->with(['depot', 'orders.items', 'orders.address'])
            ->find($runId);
    }

    public function markDispatched(DeliveryRun $run, Vehicle $vehicle, Driver $driver): void
    {
        $run->fill([
            'vehicle_id' => $vehicle->id,
            'driver_id' => $driver->id,
            'status' => DeliveryRunStatus::Dispatched,
            'dispatched_at' => now(),
        ])->save();

        $run->statusHistory()->create([
            'status' => DeliveryRunStatus::Dispatched,
            'changed_by' => auth()->id(),
        ]);
    }
}
```

Sending a run out and recording that it went out are one fact landing in two tables. The repository is the only place that knows those two writes travel together, so no caller can do half the job. The vehicle repository is thinner still: it asks the fleet for whatever is free that day and picks the truck you named.

Then the model, and the part I said I would walk back.

```php
class Vehicle extends Model
{
    public function scopeAvailableOn(Builder $query, CarbonInterface $date): void
    {
        $query->where('is_active', true)
            ->whereDoesntHave('maintenanceWindows', fn (Builder $window) => $window
                ->whereDate('starts_at', '<=', $date)
                ->whereDate('ends_at', '>=', $date))
            ->whereDoesntHave('runs', fn (Builder $run) => $run
                ->whereDate('scheduled_for', $date)
                ->whereIn('status', DeliveryRunStatus::occupying()));
    }
}
```

Availability is not a column on the vehicles table. It is three rules operations owns: the truck is in service, it is not booked into the workshop that day, and it is not already committed to another run. The repository asks for available trucks by name and never says what available means, so the day ops decides a truck can take a second run after 4pm, one place changes and every caller inherits the new meaning.

The weight of a run is not a column either:

```php
class DeliveryRun extends Model
{
    protected function payloadKg(): Attribute
    {
        return Attribute::get(fn (): float => $this->orders
            ->flatMap->items
            ->sum(fn (OrderItem $item) => $item->quantity * $item->unit_weight_kg));
    }
}
```

Which means the model is holding business logic while I just finished saying it is not a layer. Both are true and I would still do it this way.

**That weight calculation is the seam I trust least.** It only stays cheap because the repository pulls every order and its items in one go, and nothing in either file admits the two are related. Somebody trimming that load to speed up a listing page leaves dispatch working, still correct, now asking the database once per order, until a 40 stop run makes 40 round trips and nobody has any reason to go looking at the model.

**The other cost is the jump to definition chain (gd in vim).** Answering "what does dispatch actually query" means opening four files in sequence, and the answer is never on one screen. Cheap while the rules are stable. Less cheap at 11pm chasing an N+1.

What you get for both is that the weight rule exists once. The vendor API and the agent app go through the same service, and neither of them can skip a check, because there is no second copy of the check to skip.

One thing I wished for in Laravel is **Package by Feature** where a module would look like this:

```bash
📁 Orders/
├── OrderController.php
├── OrderService.php
├── OrderRepository.php
├── OrderEnums.php
├── OrderModel.php
```

I guess with some architecture tweaking we can achieve this but for the moment we are stuck with Package by Layer.

## Where this shape goes next

All of this is one arrangement of a much older idea, and the older idea is better documented than the arrangement. If these boundaries are doing something for you, these are the doors I would open next.

**The catalog it came from.** [Fowler's enterprise patterns catalog](https://martinfowler.com/eaaCatalog/) is where Service Layer and [Repository](https://martinfowler.com/eaaCatalog/repository.html) are actually specified, a page each. Read [Transaction Script](https://martinfowler.com/eaaCatalog/transactionScript.html) against [Domain Model](https://martinfowler.com/eaaCatalog/domainModel.html) first, because that is the fork this post is standing on. A service running one procedure per use case is a transaction script, a legitimate choice rather than a lesser one, and knowing which you are writing settles most arguments about where a rule belongs.

**Pointing the dependencies inward.** The layering here is vertical, which quietly makes the database the thing everything else is arranged around. [Hexagonal architecture](https://alistair.cockburn.us/hexagonal-architecture/), also called ports and adapters, turns that inside out: the domain sits in the middle and the database becomes one more adapter, no more privileged than the HTTP layer. [Clean architecture](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html) is the same instinct with different diagrams. Both are a bigger commitment than what this post describes.

**Announcing instead of calling.** A [domain event](https://martinfowler.com/eaaDev/DomainEvent.html) announces a delivery was dispatched and stops caring who listens. Laravel ships events in the box, which makes it the cheapest of these to try on a Tuesday.
