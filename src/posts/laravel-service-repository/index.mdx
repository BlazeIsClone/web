My `Post` model builds URLs. Not the controller, not a view helper. The model, calling `url('posts/'.$this->slug)` from the bottom of the stack.

I found it reading back a Laravel base I've been building on since May 2024. Ninety-four commits, twelve models, every resource wired the same way: Controller, Service, Repository, Model, strictly in that order.

Laravel people call this the service repository pattern. The older name is a three-layer architecture, presentation over business logic over data access, and the middle one is [Fowler's Service Layer](https://martinfowler.com/eaaCatalog/serviceLayer.html). Note it counts to three. The model is not a layer, it is what travels through them, which matters later.

Mostly it holds.

## One slug, four questions

A request hits `/posts/my-post`. The controller does one thing:

```php
$post = $this->postService->getPost(slug: $slug);
```

That is the entire data access in `Front\Post\PostController::show()`. It has no idea whether a slug lookup is one query or six. It asked for a post, it got a post or null.

The service answers a different question:

```php
public function getPost(?int $postId = null, ?string $slug = null): ?Post
{
    if ($slug) {
        return $this->postRepository->getBySlug($slug);
    }

    return $this->postRepository->getById($postId);
}
```

No SQL. It resolves which identity you meant and delegates. Admin calls it with an id, the front end with a slug, and neither learns those are different queries.

The repository is the first layer that touches the database:

```php
public function getBySlug(string $slug): ?Post
{
    return $this->post
        ->where('slug', $slug)
        ->active()
        ->first();
}
```

One place in the app knows a post is addressed by its `slug` column. Swap to a ULID and this method changes. Nothing above it moves.

Then the model:

```php
public function scopeActive(Builder $query): void
{
    $query->where('status', PostStatus::ACTIVE);
}
```

This is the part I like. The repository calls `active()` but never defines it, and never writes `where('status', 1)`. The meaning of active sits on the thing it describes.

Four questions, no overlap. What do I render, which identity did you mean, what query answers that, what does active mean.

The cost is a jump-to-definition chain. Answering "what does this page query" means opening four files in sequence, and the answer is never on one screen. Cheap while the query is stable. Less cheap at 11pm chasing an N+1.

## Every layer subtracts

The write path earns more than the read.

The controller hands over a payload and leaves:

```php
$created = $this->postService->createPost($request->getAttributes());

throw_if(! $created, RedirectResponseException::class, $this->postMessage->createFailed());
```

It never reads an attribute or names a column.

The service adds the one thing only it knows:

```php
public function createPost(array $attributes): Post
{
    return $this->postRepository->create([
        ...$attributes,
        'created_by' => $this->getAdminAuthUser()->id,
    ]);
}
```

Identity is a service concern here. A seeder calls `$postRepository->create()` directly and skips the stamp, a web request goes through the service and gets it, and neither caller has to remember which.

Then the repository, where one create becomes four writes:

```php
public function create(array $attributes): Post
{
    $categories = Arr::pull($attributes, 'post_categories', []);
    $featuredImage = Arr::pull($attributes, 'featured_image');
    $listingImage = Arr::pull($attributes, 'listing_image');

    $post = $this->post::create($attributes);

    $this->syncMedia($post, 'featured_image', $featuredImage);
    $this->syncMedia($post, 'listing_image', $listingImage);

    if ($post) {
        $post->categories()->sync($categories);
    }

    return $post;
}
```

Three `Arr::pull` calls strip everything that is not a column on `posts`. Then the row, the media, the pivot. The service handed down a flat array and never learns that posts have a pivot table. `$fillable` gates whatever is left.

Each layer adds or removes something, and nothing downstream trusts anything upstream. That is the strongest argument the pattern has.

The cost is the payload itself. `post_categories`, `featured_image`, and `listing_image` are keys the repository knows to pull, and nothing types or documents that contract. Spell one wrong in a new caller and it sails through the service, misses the `Arr::pull`, reaches `Post::create()`, and `$fillable` drops it. You get a post with no categories and no exception to tell you why. Array-shaped contracts between layers buy flexibility at the price of every mistake being quiet.

## Repositories that call services

Four repositories inject a service. `PostRepository`, `CustomerRepository`, `PostCategoryRepository`, and `SettingRepository` all take `MediaService`.

The reason is in the create method above. `syncMedia()` has to run in the same operation as the write, because the media rows attach to the model that was just created. Splitting it would mean a two-phase write in the service, worse in a different way.

The cost is that the stack stops having a direction. Once a repository depends on a service, "which way does this call go" is no longer answerable from the layer names, and that is most of what layer names are for.

It also produced dead code no boundary caught. `HandlesMedia` declares its own constructor, every repository using the trait declares one too, and a class method beats a trait method in PHP without so much as a warning. The trait constructor is discarded in all four cases, which is exactly why each repository re-declares `private MediaService $mediaService` itself. Two base class accessors have the same shape: `BaseMessage::modelName()` and `FrontBaseController::settingService()` both call themselves forever, and neither has blown a stack because all ten `Message` subclasses override the first and nothing calls the second.

## The model knows too much

Back to the URL that started this.

```php
public function getUrlAttribute(): string
{
    return url('posts/'.$this->slug);
}
```

`PostCategory` does the same. `Invoice` goes further, minting an encrypted session id with `Crypt::encryptString($this->id)` before returning `route(CheckoutRoutePath::SHOW, ...)`. Three of twelve models reach up into HTTP this way.

It buys real convenience. `$post->url` works in any Blade view with no helper, no presenter, nothing passed down. It costs having the front end route shape encoded in the model, so moving posts means editing the model layer, and `Post` stops being something you can reason about without knowing what the router does. The `Invoice` one is sharper, since reading a property now has an encryption side effect. That belongs in a service.

Not every blur is worth fixing. `scopeActive()` defines what active means, `PostRepository::getActive()` wraps it, `PostService::getActivePosts()` wraps that, and three layers touch one filter. I would keep that one. The definition sits in the right place and the wrappers cost a file jump rather than a duplicated `where`.

Which puts me on an odd side of the usual argument. The standing critique of this pattern family is [the anemic domain model](https://martinfowler.com/bliki/AnemicDomainModel.html), Fowler's name for services absorbing all the behavior while models decay into data bags. My services are thin enough to qualify. My models never went hollow, because scopes, casts, accessors, and media collections all stayed on them. So I did not end up anemic, I ended up with the opposite leak. Both are failures of the same boundary from different sides, and only one of them has a famous name.

## What I would keep

The service layer, without hesitation. It made `created_by` stamping one line instead of something every controller has to remember.

The repository, but as a query home rather than a substitution seam. Naming the layer stops queries scattering into controllers and traits, and that alone paid for itself. Nothing was ever swapped in twenty-one months, and the per-model interfaces I skipped have cost me nothing I have felt. The bill for that is testing, since with no interface there is no seam to hang a fake on, and `tests/` currently holds Breeze auth scaffolding and nothing else.

What I would actually change is smaller: get `url` and `checkout_link` out of the models before a second front end makes those routes wrong.

If you are adding this shape to a Laravel app, add the service first and run without the repository for a while. You will find out quickly whether you miss it, and if you do, you will know what you actually want it to do.
