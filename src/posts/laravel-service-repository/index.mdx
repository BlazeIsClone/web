When a software system is successful it keeps earning new work, and every enhancement lands on top of the layers already there. Over time that new work slows down, and the usual answer is to refactor, or to decouple logic into a separate service.

We have all seen complicated code, and pretty often the reason is application logic coupled with database logic. Business rules and queries sharing a method make a system harder to change, harder to test, and harder to hand to somebody else.

Three-layer architecture, presentation over business logic over data access, and the middle one is [Fowler's Service Layer](https://martinfowler.com/eaaCatalog/serviceLayer.html). Note it counts to three. The model is not a layer, it is what travels through them, which matters later.

Mostly it holds.

A delivery company shows where better than a blog does. I spent a stretch on a delivery management system, a couple hundred drops a day, dispatchers on a web panel and drivers on a phone. The code below is Laravel-shaped, and illustrative rather than lifted from it.

## One tracking number, four questions

A customer opens a tracking page. The controller does one thing:

```php
class TrackingController extends FrontBaseController
{
    public function show(string $trackingNumber): View|RedirectResponse
    {
        $delivery = $this->deliveryService->getDelivery(trackingNumber: $trackingNumber);

        if (! $delivery) {
            return redirect()->route($this->trackingRoutePath::INDEX)
                ->withErrors($this->deliveryMessage->notFound());
        }

        return view($this->trackingRoutePath::SHOW, [
            'delivery' => $delivery,
        ]);
    }
}
```

That is the entire data access in the tracking controller. It has no idea whether resolving a tracking number is one query or six.

The service answers a different question:

```php
class DeliveryService extends BaseService
{
    public function getDelivery(
        ?int $deliveryId = null,
        ?string $trackingNumber = null,
        ?string $orderNumber = null,
    ): ?Delivery {
        if ($trackingNumber) {
            return $this->deliveryRepository->getByTrackingNumber($trackingNumber);
        }

        if ($orderNumber) {
            return $this->deliveryRepository->getByOrderNumber($orderNumber);
        }

        return $this->deliveryRepository->getById($deliveryId);
    }
}
```

No SQL. It resolves which identity you meant and delegates. One thing, three names: the dispatcher has an internal id, the customer has a tracking number, and the client's own ERP has an order number it invented years ago and will not be changing. Enterprise systems accumulate identities, and the service is where you absorb that.

The repository is the first layer that touches the database:

```php
class DeliveryRepository extends BaseRepository
{
    public function getByTrackingNumber(string $trackingNumber): ?Delivery
    {
        return $this->delivery
            ->where('tracking_number', $trackingNumber)
            ->trackable()
            ->with(['driver', 'route', 'statusHistory'])
            ->first();
    }
}
```

One place knows a delivery is addressed by its `tracking_number` column, and one place knows a tracking page needs the driver, route and status history loaded with it. Both change here and nowhere else.

Then the model:

```php
class Delivery extends Model
{
    public function scopeTrackable(Builder $query): void
    {
        $query->whereIn('status', DeliveryStatus::trackable())
            ->where('dispatched_at', '<=', now());
    }
}
```

This is the part I like. Trackable is a rule the operations team owns rather than a column: dispatched, not cancelled, still inside the window where a customer can see it. The repository calls `trackable()` and never defines it, so when ops decides returns stay visible another 30 days, one scope changes and every query inherits the new meaning.

Four questions, no overlap. What do I render, which identity did you mean, what query answers that, what does trackable mean.

The cost is a jump-to-definition chain. Answering "what does this page query" means opening four files in sequence, and the answer is never on one screen. Cheap while the query is stable. Less cheap at 11pm chasing an N+1.

## Every layer subtracts

The write path earns more than the read.

A dispatcher assigns a delivery to a driver. The controller hands over a payload and leaves:

```php
class DeliveryDispatchController extends AdminBaseController
{
    public function store(Delivery $delivery, DeliveryDispatchRequest $request): RedirectResponse
    {
        $dispatched = $this->deliveryService->dispatchDelivery(
            $delivery,
            $request->getAttributes(),
        );

        throw_if(! $dispatched, RedirectResponseException::class, $this->deliveryMessage->dispatchFailed());

        return redirect()->route($this->deliveryRoutePath::SHOW, $delivery)->with([
            'message' => $this->deliveryMessage->dispatchSuccess(),
            'status' => true,
        ]);
    }
}
```

It never reads an attribute or names a column.

The service adds the things only it knows:

```php
class DeliveryService extends BaseService
{
    public function dispatchDelivery(Delivery $delivery, array $attributes): bool
    {
        $driver = $this->driverService->getAvailableDriver(
            driverId: $attributes['driver_id'],
            scheduledFor: $delivery->scheduled_for,
        );

        if (! $driver || $driver->vehicle->isGrounded()) {
            return false;
        }

        $dispatched = $this->deliveryRepository->dispatch($delivery, [
            ...$attributes,
            'driver_id' => $driver->id,
            'dispatched_by' => $this->getAuthUser()->id,
            'dispatched_at' => now(),
        ]);

        if ($dispatched) {
            $this->notificationService->deliveryDispatched($delivery, $driver);
        }

        return $dispatched;
    }
}
```

This is where the business actually lives. The controller does not know a vehicle can be grounded for service. The repository does not know a customer gets an SMS.

Then the repository, where one dispatch becomes four writes:

```php
class DeliveryRepository extends BaseRepository
{
    public function dispatch(Delivery $delivery, array $attributes): bool
    {
        return DB::transaction(function () use ($delivery, $attributes) {
            $stops = Arr::pull($attributes, 'route_stops', []);

            $saved = $delivery->fill([
                ...$attributes,
                'status' => DeliveryStatus::DISPATCHED,
            ])->save();

            $delivery->stops()->sync($stops);

            $delivery->statusHistory()->create([
                'status' => DeliveryStatus::DISPATCHED,
                'actor_id' => $attributes['dispatched_by'],
            ]);

            return $saved;
        });
    }
}
```

The row, the stops pivot, the status history entry, and a transaction around all of it so a half-dispatched delivery never exists. The service handed down a flat array and never learns that stops live in a pivot table.

Each layer adds or removes something, and nothing downstream trusts anything upstream. That is the strongest argument the pattern has.

## Where this shape goes next

All of this is one arrangement of a much older idea, and the older idea is better documented than the arrangement. If these boundaries are doing something for you, these are the doors I would open next.

**The catalog it came from.** [Fowler's enterprise patterns catalog](https://martinfowler.com/eaaCatalog/) is where Service Layer and [Repository](https://martinfowler.com/eaaCatalog/repository.html) are actually specified, a page each. But read [Transaction Script](https://martinfowler.com/eaaCatalog/transactionScript.html) against [Domain Model](https://martinfowler.com/eaaCatalog/domainModel.html) first, because that is the fork this post is standing on. A service running one procedure per use case is a transaction script, a legitimate choice rather than a lesser one, and knowing which you are writing settles most arguments about where a rule belongs. [Unit of Work](https://martinfowler.com/eaaCatalog/unitOfWork.html) is worth the page too, since that `DB::transaction` call is a hand-rolled corner of it.

**Pointing the dependencies inward.** The layering here is vertical, which quietly makes the database the thing everything else is arranged around. [Hexagonal architecture](https://alistair.cockburn.us/hexagonal-architecture/), also called ports and adapters, turns that inside out: the domain sits in the middle and the database becomes one more adapter, no more privileged than the HTTP layer. [Clean architecture](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html) is the same instinct with different diagrams. Both are a bigger commitment than what this post describes.

**Letting reads and writes diverge.** The tracking page needs three relations eager loaded; the dispatch panel needs rules enforced and four writes in a transaction. Same table, opposite needs. [CQRS](https://martinfowler.com/bliki/CQRS.html) is what happens when you stop making those two share a model, and Fowler is refreshingly blunt about when it is overkill.

**Announcing instead of calling.** `dispatchDelivery` names a notification service, so the dispatch rule now knows SMS exists. A [domain event](https://martinfowler.com/eaaDev/DomainEvent.html) inverts that: the service announces a delivery was dispatched and stops caring who listens. Laravel ships events in the box, which makes it the cheapest experiment here.
